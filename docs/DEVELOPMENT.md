# 开发历程与踩坑

> 这份文档记录**为什么长成现在这样**。里面每一条都是真实踩到的坑，附上「怎么发现的」——
> 因为发现方式往往比修复本身更值得复用。

---

## 一、调研先行：先把真实 Jev 的契约钉死

动手前先把 TypeSafe Jev 的接口契约调研清楚，这一步的产出直接决定了几处关键设计。

**调研到的事实**（完整版见 [`JEV-COMPAT.md`](./JEV-COMPAT.md)）：

- 端点 `POST https://api.typesafe.ai/v1/systemone`，请求体 `{model, state, questions}`，无状态、无 system prompt。
- 三种题型 `noul` / `choice` / `score`，答案形状分别是
  `{type, noul}` / `{type, choice, probabilities, confidence}` / `{type, score, legend, probabilities, confidence}`。
- **`noul` 答案没有 `confidence`**（官方原文「Noul answers don't carry one」）。
- `choice` 上限是 **255** 个选项；`score` 是 **2–10** 档；`score` 的值是**档位下标的概率加权期望**。

**调研纠正了三个原以为的设定：**

| 原本以为 | 实际 |
|---|---|
| choice 最多 4 个选项 | Jev 支持 **255** 个。「4」是我们自己的规格（需求方指定），所以代码里把它做成 `--max-options` 可放宽，并在 `provenance.limits` 里注明「这是本技能的规格」 |
| 响应里有个 `completion` 之类的文本字段 | **不存在任何文本/推理字段**。这直接决定了第二步的校验器必须拦住「请选出正确答案并说明理由」这类问题 |
| `confidence` 是「答案正确的概率」 | 它是**分布集中程度**的统计量，且**算法未公开** |

最后一条影响最大，见第四节。

## 二、第一步：识别器为什么是「打分 + 阈值 + 回问」，而不是「让模型说」

第一版想过最省事的做法：把输入丢给模型，让它输出领域名。放弃了，原因很实际——
**这个技能的卖点之一是可复现**，而「让模型说」既不能 diff 也不能解释。

改成规则打分后，第一个真实问题立刻出现：

```
输入：求导数的英文表达是什么？
```

「导数」命中数学，「英文」命中英语，两边都拿分。谁的词表长谁赢——这显然不对。

**解法：反证词（`excludes`）。** 每个领域不只列「什么属于我」，还要列「什么不属于我」。
数学把「英语/单词/时态」列为反证（扣分），英语把「方程/导数/积分」列为反证。
上面那句于是两边互相扣分 → 都拿不到高分 → 置信度低于 0.55 → `decision: "ask"`。

**这个结果是对的**：这种输入确实不该由规则决定，应该问用户。反证词的真正价值不是「让它猜对」，
而是**让它在不该猜的时候承认自己不该猜**。

> 后来给这条写了两个互补的测试：一个验证反证词真的扣分（`求导数的英语表达` 里数学被扣），
> 一个验证它不会误伤（含/不含反证词的同一句话，数学得分必须前者低于后者）。
> 只写前者的话，一个「把所有领域都扣到 0」的 bug 也能通过测试。

## 三、第二步：三处「产物合法但答案是错的」的坑

这三条都属于最阴的一类 bug：**JSON 完全合法、测试全绿、用户看不出问题**。

### 坑 1：全角冒号让第一个选项消失

```js
// 最初的选项标记正则：前缀只认 空白 / 全角分号 / 半角分号 / 竖线
const MARKER_RE = /(?:^|[\s\u3000；;|])(?:...)/gm;
```

输入 `选一个：A. 甲 B. 乙 C. 丙 D. 丙` —— `A` 前面是全角冒号 `：`，不在前缀字符类里，
于是 **A 被整个丢掉**，只抽到 B、C、D 三个选项。

三个选项也是合法的（≥2），产物照样产出，`validateQuestionSet` 照样通过。
**只有一条「选项数与标签序列」的断言能抓住它。**

修复时顺手把全角句号 `。` 也加进前缀——中文题干里同样常见。

### 坑 2：把「求解题」包成命题

数学的判断题模板最初长这样：

```js
instructions: `命题「${input}」成立。`    // ← 输入是「解方程 x²-5x+6=0」时会生成
                                          //   「命题「解方程 x²-5x+6=0」成立。」—— 完全没意义
```

**根因是把「结构条件」当成了「语义条件」**：模板的 `needs` 只能判断「输入里有没有选项」，
判断不了「这个输入是不是一个命题」。

**解法：给模板加第二层守卫 `when`。**

- 数学判断题：输入以「解/求/计算/化简/证明/求证」开头就跳过（那是任务，不是命题）；
- 英语语法判断题：输入里至少要有 3 个英文词才生成（「把这句话翻译成英语」里没有英文句子）。

顺带把 noul 的问法从「命题『…』成立」改成**直接用问句**（「上述数学命题在实数范围内成立吗？」）——
Jev 官方文档写的是 "The yes/no question the model answers, **or** a statement for it to judge"，
问句本来就是合法形态，而且不必强行把用户的输入改写成命题。

### 坑 3：「其他」这条建议不能一刀切

Jev 官方建议：选项可能覆盖不全时加一个 `other` / `none of the above`。
第一版把它做成了「choice 有 ≥3 个选项又没有『其他』就警告」。

然后数学四选一被警告了——**但数学题加「以上都不是」是错的**。

**解法：靠题目自带的 `kind` 区分，而不是猜选项文字。**

```js
kind: 'answer'    // 答案型：数学/英语的四选一，「其他」是错误选项
kind: 'classify'  // 归类型：属于哪一类，「其他」是必需的退路
```

`kind` 只在信封与校验里使用，**不进 Jev 请求**（`toJevQuestion` 只取 `type/instructions/criteria`）——
约束就是约束，多一个字段发出去就不是 Jev 的契约了。

## 四、第三步：为什么概率不能让模型直接给

最初的设计是「让模型输出每个选项的概率」。自己试了几次就放弃了：

- 要么得到 `0.25 / 0.25 / 0.25 / 0.25`（假均匀）；
- 要么得到 `0.99 / 0.005 / 0.003 / 0.002`（假自信）。

**两种都不是校准，只是把模型的口头自信装扮成数字。**

改成「模型只给支持度（任意实数）+ 依据，引擎做 softmax」之后：

1. 概率天然合法（和为 1、无负数）；
2. **平移不变**——模型给 `3/1/1` 与给 `300/100/100` 结果完全相同，所以模型不需要「会调温度」；
3. `derivation` 里留下了原始支持度与温度，**任何人都能用纸笔复算**。

### 置信度：撞上了一个自相矛盾的官方数据

`confidence` 想照抄官方口径，但官方**没有公布算法**，只说「concentrated = high」。
于是拿官方公布的样例反推，发现的不是公式，而是**矛盾**：

| 官方公布的分布 | 官方 confidence |
|---|---|
| `{0, 0.16, 0.84}` | 0.76 |
| `{0.001, 0.159, 0.84}` | **0.596** |

两个几乎是同一个分布，官方给了 0.76 和 0.596。**这说明它的 confidence 不是所显示概率的纯函数**
（多半还用了未舍入的内部概率或 logits）。

结论：**这是个不透明的厂商统计量，照抄不了。** 所以改成「公开自己的定义」：

```
confidence = 0.75 · (p₁−p₂)/(1−p₂) + 0.25 · (1 − H/ln n)
```

`w = 0.75` 是**对着官方 6 组样例拟出来的**，平均绝对误差 0.067（对照表在 `docs/DESIGN.md` 里）。
第三组差 0.160——但那一组的官方值本身就自相矛盾，所以这个差异是**可解释**的。

TypeSafe 自己也留了口子：「you are never locked into our definition… which is exactly why we give you
the full `probabilities` in the response.」——**知道公式比拿到一个不可解释的数字更有用**。

### 一个测试抓出的真 bug：答案类型与题目类型不一致

`validateJevResponse` 最初只逐个校验答案自身的形状，没检查「答案的 type 是否等于题目的 type」。
于是 **`noul` 题收到一个合法的 `choice` 答案时，校验通过**。

这个 bug 是写测试时撞出来的（测试断言「给 choice 题一个 noul 答案应当失败」，结果它通过了）。
修复后会在 `answers.<id>` 上报出「答案 type 是 noul，但题目是 choice」。

### 同一个 bug 出现了两次：`null` 覆盖默认参数

```js
function f({ model = 'jev-latest' } = {}) {}   // 默认参数只在 undefined 时生效
f({ model: null });                            // → model 是 null，不是 'jev-latest'
```

第一次的表现是 `response.model` 变成 `"jev-agent/null"`；第二次是 `request.model` 变成 `null`，
并且直到 `makeEnvelope` 的信封校验才炸——**错误离原因太远**。

修复方式是 `model || DEFAULT_MODEL`（而不是依赖默认参数），并在两处都加上：
一处修好不算修好，因为漏掉的那处会在别的调用路径上复现。

## 五、渲染层：一个会误导读者的显示 bug

端到端演示第一次跑通时，科学那道打分题的输出是：

```
   0 ████████████········  58.6%
   1 ███████·············  35.5% ←
   ...
  score：0.5014　最可能的档位：第 1 档 —— 含常见迷思…
```

**箭头指向第 1 档，但最高的柱子是第 0 档。** 原因是高亮用了 `Math.round(ans.score)`：
`0.5014` 四舍五入是 1，而概率最大的其实是第 0 档。

`score` 是概率加权期望，**本来就可以落在两档之间**，用 `round` 去反推档位是概念错误。

修复：高亮改用概率的 argmax；两者不一致时**显式提醒**——

> 注意：加权期望四舍五入到第 1 档，但概率最大的档位是第 0 档。
> 需要离散判决时用 `--round-score` 明确取整档，不要自行四舍五入。

这一类 bug 值得单独写回归测试（`test/render.test.mjs` 里那条），因为**它不会让任何校验失败**——
它只会让读者照着箭头走到错的档位。

## 六、真实使用暴露的四个缺陷（首次实战）

第一位真实用户问的是「乌克兰无人机袭击俄罗斯莫斯科 Kapotnya 区的最新图像」——一句话就撞出了四个缺陷。

### 缺陷 1（严重）：判错领域，而且判得很有把握

输入被判成**英语**，置信度 **74.3%**，`decision: "auto"`。

两个原因叠在一起：

1. **时政词典缺词**：`乌克兰`、`俄罗斯`、`无人机`、`袭击`、`炼油厂` 一个都没有，
   所以时政拿 0 分；
2. **英语靠一个弱模式拿到 1 分**：`中英混排` 模式匹配了「莫斯科 Kapotnya 区」——
   那是拉丁字母**音译**，不是英语。

然后最关键的一步：**只有 1 分，却算出了 0.743 的置信度并自动采用。**
因为 `share` 与 `margin` 在「只有一家得分」时会自动拉满——**没有竞争者被当成了高度确信**。

修复分三处，缺一不可：

- 时政词典补国际冲突/军事/能源设施类词汇与「无人机+袭击」这类组合模式；
- `中英混排` 模式要求英文两侧**有空格**（真双语行文长这样：「这个 phrase 很常见」）；
- **加 `min_evidence_mass` 硬闸门**：证据量低于 2.5 一律 `ask`，不看置信度。

第 3 条是真正重要的那条。前两条只是补数据，第三条才堵住了机制漏洞——
**这个洞会让任何领域的任何一条弱词单独定案**，今天踩到「英语」，明天可能是别的。

> 教训：**「置信度」不能只由分布形状（优势占比、领先幅度）构成，因为它会在没有竞争时虚高。**
> 必须另有一道与分布形状无关的证据量闸门。

### 缺陷 2：日期被算术表达式模式吃掉

时政新闻里写着「2026-09-20」，数学的 `算术表达式` 模式把它匹配成了减法 `2026-0`，
给数学凭空加 3 分，把时政的置信度从 0.84 压到 **0.50**，判成了 `ask`。

第一版修复只加了 `(?<![\d.])`（防止从 4 位年份中间起算），**没修好**——
正则引擎会从「-」后面重新起算，「09-20」照样匹配。补上 `-` 与 `/` 之后
`2026-09-20` 与 `12/31/2026` 才都被挡住，而 `12-5`、`2+3`、`-5+3`、`x²-5x+6=0` 仍然正常命中。

> 教训：**修正则时不要只验证「坏例子被挡住了」，一定要同时验证「好例子没被误伤」。**
> 这两件事的测试要写在同一条用例里，否则很容易修成另一个方向的错。

### 缺陷 3：「Astra」被读成化学式

科学里的 `化学状态标记` 模式（`(aq|s|l|g)`）把「**As**tra」拆成 `A` + `s`（固态标记），
给科学加分。顺带发现 `Gas` 会被拆成 `Ga` + `s`。

修复时又发现**原模式另一种形式的错**：它要求化学式至多 3 个字符，
结果真正该匹配的 `NaCl(aq)`、`AgNO3(aq)` **匹配不上**——假阳性掩盖了假阴性。

最终改成：化学式允许多段 `(?:[A-Z][a-z]?[0-9]*){1,4}`，且**状态标记必须带括号**。
真化学照常命中，`Astra`/`Gas` 不再误报。

> 教训：调条件时很容易只盯着假阳性，顺手把假阴性带出来。
> 两种都要写测试（这条用例现在同时断言 `NaCl(aq)` 命中、`Astra` 不命中）。

### 缺陷 4：CLI 不支持「一次请求问多个问题」

Jev 官方最强调的工程建议就是**同一 state 的所有问题放在一次请求里**（并行评估、
互相看不见答案），SKILL.md 里也写了这一条。但 `jev ask` 只能 `--pick 一个`——
**文档说了、代码做不到**。

修复：`--pick` 支持 `1,2` 多选，且 `--custom` 与 `--pick` 可以并用
（「我自己加一个问题，另外把第 2 条也一起问了」是很自然的用法），并去重。

> 教训：**写文档时提到的「推荐用法」，回手就该检查代码支不支持。** 不然文档会变成谎话。

### 除此之外，第一步做对了一件事

同一句话在修好之后重新跑：**时政 96.2%，`auto`**，数学与科学都是 0 分。
`truth_apt` 检查也正常工作——它没有把「最新图像」这个没有真值的表述放过去。

## 七、领域词典的真实缺口

演示用的科学例子「人类的大脑只被使用了 10%」最初**识别不出来**——科学词典里居然没有
「大脑」「神经元」这类神经科学词汇，于是 `mass = 0` → `decision = "ask"`。

两条应对，都保留了：

1. **补词**（`神经元`/`突触`/`神经科学` 进强词，`大脑`/`脑细胞`/`认知` 进中词）；
2. **不改设计**：`mass = 0` 时判 `ask` 是对的——**没有证据就不要猜**。词典覆盖率永远有边界，
   而「承认不知道」比「猜一个」便宜得多。

## 八、开发顺序（供参考）

1. 调研真实 Jev → 写 `JEV-COMPAT.md` 的事实部分；
2. 定契约（`lib/schema.mjs`）——**先定数据形状再写逻辑**，后面所有模块都被它约束；
3. 领域层（6 个领域的词典、等级集、模板、判题要点）；
4. 三步流水线（identify → questions → decide）+ provider；
5. CLI；
6. 测试（142 个）——**测试写在演示之前**，因为演示会暴露的坑，测试能提前挡住一部分；
7. 端到端演示 → 撞出渲染 bug 与词典缺口；
8. 文档（`DESIGN.md` / `SCHEMA.md` / `JEV-COMPAT.md`）——**趁记忆还新鲜**写取舍，
   尤其是「为什么不用另一种做法」。

## 九、第三个输入：一句话让技能多长出一个领域

输入：「我的订单已经三天没有发货了 选项 物流、退款、产品故障、其他」

这是 **Jev 官方最典型的用例**（工单分流），但技能第一步如实报了 `ask`——**六个领域全 0 分**。
这是**正确的行为**：这个输入确实不属于原来那五个领域，引擎没有硬猜，而是要求确认。
（对比第二次实战那次「判错领域还很有把握」——这次的 `ask` 正是修好之后的正确反应。）

于是做了三件事。

### 1. 加了第六个领域「客服」，并验证了扩展机制真的好用

按设计好的路径：新建 `lib/domains/service.mjs` + 在 `index.mjs` 的 `BUILTIN` 加一行。
**没有改任何其他代码**，而领域结构完整性测试（词典/题型适配/等级集/模板/判题要点/noulCriteria）
**自动覆盖了新领域**——这是当初把「领域自带完整结构」写成断言的好处。

客服领域值得单列，因为它的判断逻辑与学科类**方向相反**：

| | 学科类 | 客服 |
|---|---|---|
| 判什么 | 知识**对不对** | 诉求**归到哪个流程** |
| 典型陷阱 | 迷思、时效、单位 | 把「问题出在谁身上」当成「客户要什么」 |
| noul 的性质 | 事实判断（可核查） | **事实抽取**（原话里有没有） |

所以它的 `judgeHints` 写成分流规则：**「资金 > 货物 > 解释」的诉求优先级**、
**「其他」是兜底类别不是「不确定」，一旦选中应交人复核**。
并且加了回归测试确认**新领域没有抢走原有领域的输入**——
客服词典含「退货/保修」，与常识的消费维权词汇相邻，不验证很容易把常识题带偏。

### 2. 自然语言选项列表「选项 物流、退款、产品故障、其他」抽不出来

这是最刺眼的一条：**用户完全按 Jev 的用法提问**（给人看的 criteria map 文字版），
而只认 `A. … B. …` 的抽取器说「抽不到选项」。等于是工具拒绝了最标准的用法。

加了第二条抽取路径，三重守卫（必须先有列表标记词、每项必须是 ≤16 字的短标签、
2–8 项不重复），所以「今天买了苹果、香蕉、橙子」这种普通顿号并列不会被误判成选项。

> 踩坑：兜底代码写在了 `extractOptions` 最后一个 `return` **之后**——
> 而它前面有一串 `if (...) return []` 的提前出口。**代码写了、路径到不了、
> 测试也测不出来**（因为测试直接调 `extractOptionList` 而不走 `extractOptions`）。
> 修法是把标记式逻辑抽成 `extractOptionMarkers`，让 `extractOptions` 变成
> 「标记式优先，不合法就退到自然语言列表」的两行分流。

### 3. 选项留在 state 里会污染判断

`state` 是「要被判断的内容」。用户写「我的订单三天没发货了 选项 物流、**退款**、产品故障、其他」，
如果选项列表留在 state 里，判断时**极易把「退款」当成客户说过的话**——
一条物流工单就会被分到退款队列。选项是**给工具的指令**，不是客户的内容。

所以加了 `stripOptionList`：自然语言列表从 state 剥掉，**标记式不剥**
（`A. … B. …` 是题干的一部分，Jev 官方示例里 state 就是完整题目）。
判断的 basis 里也专门写了这一条，因为它是本例最容易出错的点。

### 4. 顺带：无描述的选项警告合并成一条

自然语言列表一次给出 4 个没有描述的选项，逐个报会刷 4 条一模一样的警告，
把真正的问题淹掉。改成一条汇总。

> 这条警告本身是有价值的：**「标签够清楚所以不用描述」在学科类里成立，在分流任务里不成立**——
> 分流的边界恰恰要靠描述来划（「退款」到底含不含「退差价」？）。所以产物是
> 「通过（有警告）」，而警告被如实保留在 `jev verify` 的输出里。

## 十、如果要继续开发

**优先候选**（按性价比排序）：

1. **真实 Jev 适配器**：`--provider typesafe`。契约已经逐字段对齐了，只需要一个 `fetch`
   到 `/v1/systemone` + 429/529 退避重试。有了它就能**在同一套问题上对比本技能与真实 Jev**，
   这是最有价值的一步。
2. **更多领域**：历史、地理、编程、医学……登记表已经做成可扩展的
   （加一个 `.mjs` + `BUILTIN` 一行），测试会自动覆盖新领域的结构完整性。
3. **批量模式**：`jev batch --states states.jsonl --questions q.json`。Jev 官方实测
   一次问 13 个问题的成本远低于问 13 次（便宜 11.5 倍、快 9.6 倍），
   而本技能现在的 CLI 是单条设计的。
4. **一致性的自动化**：现在 `--samples` 只对 `provider=deepseek` 有效。
   可以加「同一问题换措辞重问 N 次，看结论是否稳定」——
   这正是官方 jaggedness 文档里「措辞敏感」那条的对应测量。
5. **校准闭环**：把 `jev calibrate` 的结果写进档案，并在下次决策时提示
   「在你这种领域上，我们的 confidence 平均偏高 0.15，建议把阈值上调」。
