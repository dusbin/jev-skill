# 设计文档

> 数据契约见 [`SCHEMA.md`](./SCHEMA.md)；与真实 TypeSafe Jev 的对照见 [`JEV-COMPAT.md`](./JEV-COMPAT.md)；
> 开发历程与踩坑见 [`DEVELOPMENT.md`](./DEVELOPMENT.md)。

## 要解决的问题

「给我一个带概率的判断」——这句话里藏着四个坑，每一个都能把结果做废：

1. **概率是编出来的**。让 LLM 直接输出「四个选项的概率」，得到的是假均匀（`0.25×4`）或假自信（`0.99/0.005/…`）。
   那不是校准，只是把模型的口头自信装扮成数字。
2. **领域错了，后面全错**。同一句「这句话对不对」，在英语里问的是语法，在时政里问的是事实一致性，
   在常识里问的是安全做法。领域判错时，**用户从输出上看不出来**——产出的 JSON 依然完美。
3. **问题问坏了，答案再准也没用**。「A 和 B 都成立吗」是一个调用里问了两个问题；
   「请选出正确答案并说明理由」是在要求 Jev 生成文本；「选项超过 4 个」直接违反上限。
   这些错误在提问时只值一行警告，到出结果时就是一份废掉的产物。
4. **不确定性被藏起来**。低置信、多次采样互相矛盾、state 里被人塞了「忽略以上指令」——
   这些都必须出现在结果里，而不是被一段流畅的说明文字盖过去。

## 分工：判断交给模型，数学交给引擎

```
                    ┌──────────────────────────────┐
   用户输入 ──①──→ │ identify   领域识别（规则打分）│──→ domain.json
                    └──────────────────────────────┘
                    ┌──────────────────────────────┐
        ──②──→     │ questions  出题 + 质量校验   │──→ questions.json（= 合法 Jev 请求）
                    └──────────────────────────────┘
                    ┌──────────────────────────────┐
        ──③──→     │ decide                        │──→ decision.json（固定 JSON）
                    │  ├ 模型：给支持度 + 依据      │
                    │  └ 引擎：softmax / 置信度 /   │
                    │          score / 结构校验     │
                    └──────────────────────────────┘
```

| 谁 | 负责什么 | 为什么是它 |
|---|---|---|
| **模型** | 读 state、比较选项、指出依据、给支持度 | 这是语言理解，模型最擅长；且换任何模型都成立 |
| **引擎** | softmax 归一、置信度、概率加权期望、全部结构校验 | 确定性、可复现、可测试、可 diff；出错时是 bug 而不是「模型这天状态不好」 |

**这条分界带来一个不显然的好处**：模型给 `3/1/1` 和给 `300/100/100`，引擎算出的结果**完全相同**，
因为 softmax 只在乎差值。所以模型不需要理解温度、不需要会调概率、不需要被反复叮嘱「要校准」——
它只需要说清「哪个更可能、为什么」。

## 一、领域识别（`lib/identify.mjs`）

### 为什么不让模型直接说领域

| 朴素做法 | 问题 |
|---|---|
| 让模型输出领域名 | 不可复现、不可解释；同一个输入两次可能给不同答案；无法回答「凭什么」 |
| 关键词硬匹配 | 一条命中就定案，「求导数的英语表达」会被判成数学或英语，看谁先匹配 |
| 让用户永远自己选 | 把负担甩给用户，而这个技能的价值之一就是替他省这一步 |

### 实际做法：加权证据 + 三类不确定性

```
每个领域 raw = Σ(强词 3 / 中词 2 / 弱词 1) × min(出现次数, 3)
              + Σ 正则模式权重
              − Σ 反证词惩罚

置信度 = 0.35 · 优势占比归一 + 0.35 · 领先幅度 + 0.30 · 证据量饱和
         优势占比归一 = (top_share − 1/n) / (1 − 1/n)
         领先幅度     = (raw₁ − raw₂) / raw₁
         证据量饱和   = mass / (mass + 6)
```

**三项缺一不可**，各自堵一个漏洞：

- **优势占比**：防止「一分险胜」被判为确定（5 个领域时均匀占比是 0.2，要做归一，否则一命中就有 0.2 底分）。
- **领先幅度**：防止「总分很高但两家咬得紧」（例如数学 12 分、英语 11 分）。
- **证据量饱和**：防止「只命中一个词就判案」。`mass/(mass+6)` 在证据少时压得很低，且会饱和——
  再多同义词也不会把置信度刷到 1。

**反证词是这套里最关键的设计。** 没有它，任何领域只要出现「英语」两个字就会拿分。
有了它，`求导数的英语表达` 里数学会被 `英语` 扣分、英语会被 `导数` 扣分，两边拉平 → 置信度低于阈值
→ `decision: "ask"` → 回问用户。**这正是我们希望它做的事**：这种输入确实不该由规则决定。

### 低于阈值时不猜

```js
if (mass <= 0)                    decision = 'ask';   // 完全没有证据
else if (confidence < 0.55)       decision = 'ask';   // 证据不足以定案
```

`decision: "ask"` 时 `domain` 被置为 `other`，但 `decided_domain` 与 `candidates` 都保留下来供人判断。
SKILL.md 里把这条写成红线：**不许替用户决定领域**。

> 阈值 0.55 与三项权重都在 `IDENTIFY_TUNING` 里，改它必须同步测试与本文档。

## 二、出题与校验（`lib/questions.mjs`）

### 选项抽取：宁可抽不到，也不要抽错

中文题目的选项形态极杂：`A.` / `A、` / `（A）` / `A：` / `①` / `1.` / 全角括号 / 一行内连续。
标注器只接受有把握的形态，并且做三道自检：

1. 标签必须是 `A–D`、`①–④` 或 `1–4`，且**数量 ≥ 2**；
2. 标签不能重复；
3. 数字标签**必须从 1 连续**——否则那更可能是题干里的步骤编号（「第 2 步…第 5 步…」）而不是选项。

**抽不到就返回空数组，由调用方去问用户补。** 猜错选项比没有选项严重得多：选项会改变模型看题的方式，
而错得悄悄无声——产物依然合法，只是答案在回答另一个问题。

> 踩过的坑：标记正则的前缀字符类里漏了全角冒号 `：`，导致「选一个：A. 甲 B. 乙」只抽到 B、C、D 三个选项。
> 产物完全合法，测试也全绿——**这类 bug 只能靠「选项数与标签序列」的断言抓**（见 `test/questions.test.mjs`）。

### 三种题型怎么选

领域的 `questionFits` 给出每种题型的适配度与**理由**（理由会显示给用户，让他明白为什么推荐这个题型）：

| 领域 | 最强题型 | 为什么 |
|---|---|---|
| 数学 | choice | 答案是一个确定值，四选一天然成立 |
| 英语 | choice | 语法/词义辨析的标准形态就是四选一 |
| 科学 | noul | 「是否符合科学共识」是非黑即白，且能暴露迷思 |
| 时政 | noul | 唯一可判的形态是「事实性陈述是否与公开报道一致」 |
| 常识 | choice | 「哪种做法正确」是常识题的标准形态 |

### 模板守卫：`needs` 与 `when`

- `needs`：结构条件（有没有选项、输入里有没有一份解答）
- `when`：**这个模板在这个输入上说不说得通**

`when` 是必要的，因为有些模板在结构上成立但语义上荒谬：

- 数学判断题对「解方程 x²-5x+6=0」→「上述数学命题成立吗」**没有意义**（那是任务，不是命题）
  → `when` 用动词开头模式挡掉。
- 英语语法判断题对「把这句话翻译成英语」→ 输入里根本没有英文句子 → `when` 用「至少 3 个英文词」挡掉。

### 校验器：坏题在发出前就拦住

`validateQuestion` 分两级：

| 级别 | 内容 |
|---|---|
| **错误（必须改）** | `type` 非法；选项数超出 `maxOptions`（默认 4）；score 少于 2 档或多于 10 档；等级文字重复；noul 的 criteria 出现 `true`/`false` 以外的键 |
| **警告（改了更好）** | 选项没有描述；等级只有 1–2 个字；**归类型**题目缺「其他」；判断题里出现「和/以及/或」；instructions 里有多个问号；instructions 里要求解释理由；可能泄漏答案 |

两条规则特别值得一提：

1. **「其他」这条只对归类型成立**。数学四选一里加「以上都不是」是错的。
   所以靠题目自带的 `kind: 'classify' | 'answer'` 来区分，而不是去猜选项文字。
2. **`kind` 只在信封与校验里用，不进 Jev 请求**。`toJevQuestion` 只取 `type`/`instructions`/`criteria`——
   多一个字段发出去，就不再是 Jev 的契约了。

### 追问合规性（truth-apt）检查

Jev 输出的是**命题为真的概率**。没有真值的问题强行要概率，只会得到一个看起来像结论的噪声。
所以第二步会挡下四类问题：

| 类型 | 例子 | 为什么不给概率 | 给什么改写 |
|---|---|---|---|
| 价值判断 | 「这项政策好不好」 | 不存在真值 | 「该说法是否与公开报道一致」 |
| 要求生成文本 | 「请解释为什么天是蓝的」 | Jev 不返回文本 | 「该说法与科学共识的符合程度」打分题 |
| 复合问题 | 「这对吗？它过时了吗？」 | 一个调用一个问题 | 拆成多个 question，一次请求里并行问 |
| 预测未来 | 「明天会涨吗」 | 不是关于当前状态的命题 | 「当前证据支持 X 成立吗」 |

### 注入检查

真实 Jev 官方承认对对抗内容「不设防」。本技能的 `state` 直接来自用户输入，所以把
「忽略以上指令」「正确答案是 X」「你必须选择」这类字句**标出来**，写进 `provenance.state_injection`，
并在渲染时提示用户。

**只报警不拦截**：state 里也可能合理地出现这类字面内容（客户投诉信里就写着「你们的系统说答案是 A」），
拦掉会造成误伤。判断的责任留给读结果的人。

## 三、决策与置信度（`lib/decision.mjs`）

### 支持度 → 概率

```
p = softmax(support / T)          T = ENGINE_TUNING.softmax_temperature（默认 1）
```

为什么用 softmax 而不是让模型直接给概率：

- **平移不变**：`3/1/1` 与 `300/100/100` 结果相同，模型不需要「会调温度」；
- **恒为合法分布**：和必然为 1，不需要归一化补丁，也不会出现负概率；
- **可解释**：`derivation` 里把原始支持度、温度、每一档的概率都记下来，任何人可以复算。

### score 的定义

```
score = Σ i · pᵢ          （i 是档位下标，从 0 开始）
```

这与 Jev 完全一致（「probability-weighted mean over level indices」），所以可以为小数、可以落在两档之间。

⚠️ **但不要把它当测量值。** TypeSafe 官方明确警告评分等级的数值校准很弱，
不要用 score 推算两档之间的精确数值。所以本技能提供 `--round-score`：取概率最大的档位，
用于需要离散判决的场景（`derivation` 里仍然保留加权期望值）。

### confidence：本技能的定义（公开）

```
confidence = w · 归一化优势 + (1 − w) · (1 − 归一化熵)
归一化优势 = (p₁ − p₂) / (1 − p₂)      w = 0.75
归一化熵   = H(p) / ln(n)              H(p) = −Σ pᵢ ln pᵢ
```

**为什么两项都要**——单看任一项都会被一种坏形状骗过：

| 坏形状 | 单看优势 | 单看熵 | 两项一起 |
|---|---|---|---|
| 一个次优 + 一堆长尾（`0.5/0.25/0.125/0.125`） | 被骗（margin 0.33 看着还行） | 能看出来（熵 0.875） | ✅ **0.281** |
| 两个几乎并列（`0.45/0.44/0.10/0.01`） | 能看出来（margin 0.018） | 被骗（熵只有 0.719） | ✅ **0.084** |

`w=0.75` 是**对着 TypeSafe 公布的样例拟出来的**。以下对照表就是选它的依据：

| 官方公布的分布 | 官方 confidence | 本技能 | 差 |
|---|---|---|---|
| `{0, 0.02, 0.98}` | 0.97 | 0.962 | 0.008 |
| `{0, 0.16, 0.84}` | 0.76 | 0.757 | 0.003 |
| `{0.001, 0.159, 0.84}` | 0.596 | 0.756 | **0.160** |
| `{0.04, 0.35, 0.61}` | 0.42 | 0.369 | 0.051 |
| `{0.02, 0.24, 0.34, 0.40}` | 0.20 | 0.110 | 0.090 |
| `{0.24, 0.40, 0.34, 0.02}` | 0.20 | 0.110 | 0.090 |

**平均绝对误差 0.067。** 第三行的 0.160 不是我们算错了——是**官方自己公布的数自相矛盾**：
`{0, 0.16, 0.84}` 与 `{0.001, 0.159, 0.84}` 几乎是同一个分布，官方却给出 0.76 与 0.596。

**这说明 Jev 的 confidence 不是所显示概率的纯函数**（多半还用了未舍入的内部概率或 logits），
也就再次印证：它是个**不透明**的厂商统计量。

所以本技能的选择是：**公开公式、接受 0.067 的平均误差、让任何人都能复算**。
TypeSafe 自己也留了口子：「you are never locked into our definition… which is exactly why we give you
the full `probabilities` in the response.」需要卡阈值时，用 `probabilities` 里被选中项的概率。

### 多次采样与一致性

`--samples N`（provider=deepseek）会把 N 次采样的**概率分布取平均**，并给出：

```json
"consistency": {
  "q-xxxx": { "samples": 5, "agreement": 0.6, "flips": 2,
              "label_distribution": { "A": 3, "B": 2, "C": 0, "D": 0 } }
}
```

这不是花架子：TypeSafe 自家 cookbook 就是靠「同一套题跑 15 次、看标签一致率」评估稳定性，
并公布了它的模型在 8 个问题上有 2 个会翻转。

**一致率低的问题必须被当成「这条结论不能用于自动决策」**，而不是照旧使用——
SKILL.md 把这条写成了汇报要求。

## 四、为什么要留痕（`basis` / `derivation` / `provenance`）

三份留痕各自回答一个不同的问题：

| 字段 | 回答的问题 | 内容 |
|---|---|---|
| `judgment.basis` | **凭什么这么判** | 逐条依据，要求摘录 state 原文 |
| `derivation` | **数字是怎么算出来的** | 原始支持度、温度、归一化优势、归一化熵、期望值 |
| `provenance` | **谁、用什么、在什么限制下算的** | provider、模型名、引擎参数、限制、注入检查结果 |

判断提示里把 basis 的格式写死成 `支持 <对象>：<原文摘录> → <为什么这支持它>`，并要求「写不出摘录的依据就不要写」。
这是唯一能对抗「凭印象编」的机制——因为摘录可以被核对，印象不能。

`provenance.limits.choice_max_options` 里还写了一句
「这是本技能的规格；TypeSafe Jev 自身支持最多 255 个选项」——
**限制本身也是留痕的一部分**：看到产物的人应该知道这是谁的规矩。

## 五、可复现性

`test/pipeline.test.mjs` 里有一条断言：**同样的输入 + 同样的判断 → 除 `generated_at` 外逐字段相同**。

实现上靠三点：

1. 题目 id 是 `sha1(模板 id | 归一化输入)` 的短哈希，不是自增序号；
2. 全程不引入 `Math.random`、不读环境变量影响数值（provider 名只写在 `provenance` 里）；
3. 引擎参数是 `ENGINE_TUNING` 里的冻结常量。

所以「上周那份产物和这周差在哪」可以直接 `diff`。

## 六、校准（`lib/calibration.mjs`）

`jev calibrate` 输出 ECE / Brier / 可靠性表，并**同时给两个口径**：

- `confidence` —— 本技能的定义；
- `winning_probability` —— 被选中项自身的概率。

两者差别很大时，说明「该用哪一个」是有讲究的：**要卡阈值就用后者**（官方也这么建议）。

三条硬规矩写在代码里：

1. **样本少于 30 条时明确说「只能当趋势看」**——校准是分组性质，样本不足时测的是噪声。
2. **标注必须由人给出**。拿模型自己的结论当标准答案，测出来的只是它和自己的相似度。
3. **过度自信 / 过度保守会被主动点出来**（平均置信度与实际正确率相差超过 0.15 时）。

## 七、可调参数总表

改任何一个都必须同步测试、本文档与 `docs/JEV-COMPAT.md` 的差异表。

| 参数 | 位置 | 默认 | 影响 |
|---|---|---|---|
| `mass_saturation` | `IDENTIFY_TUNING` | 6 | 证据量饱和系数，越大越需要更多证据 |
| `weights` | `IDENTIFY_TUNING` | 0.35 / 0.35 / 0.30 | 置信度三项权重 |
| `auto_threshold` | `IDENTIFY_TUNING` | 0.55 | 低于此值判 `ask`（回问用户） |
| `tie_ratio` | `IDENTIFY_TUNING` | 0.15 | 前两名差距小于此比例时提示易混淆 |
| `softmax_temperature` | `ENGINE_TUNING` | 1 | >1 更平（更保守），<1 更尖 |
| `confidence_margin_weight` | `ENGINE_TUNING` | 0.75 | 优势项与熵项的配比 |
| `probability_digits` | `ENGINE_TUNING` | 4 | 概率舍入位数（官方示例给 2 位） |
| `choice.max` | `LIMITS` | 4 | 本技能规格，可用 `--max-options` 放宽 |
| `score.min/max` | `LIMITS` | 2 / 10 | 与 Jev 一致，不应改动 |
